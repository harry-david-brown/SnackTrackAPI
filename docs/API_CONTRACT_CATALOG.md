# SnackTrack API contract catalog

**Recorded:** 2026-08-31  
**Scope:** Every endpoint consumed by `SnackTrackApp`, including the Gmail OAuth browser callback  
**Contract version:** Existing success payloads are unversioned; operational errors target envelope version `1`

This catalog records the post-refactor cross-stack contract. The only retained rollout boundary is the released-client CSV multipart endpoint naming and redundant `userId` field described below.

## Shared transport rules

### Authentication policies

- **Public:** no access token; the app client must not attempt session refresh.
- **Bearer:** `Authorization: Bearer <accessToken>`; authenticated identity is authoritative even when a legacy `userId` field is accepted.
- **OAuth callback:** Google calls the API with a signed state value; the API redirects to the allowlisted app URI.
- `X-Timezone` is supplied by the app client on requests and may repair a user's stored IANA timezone on analytics/import-preference reads.
- `X-Request-ID` may be supplied as a short correlation identifier. The API validates or replaces it, returns it in the response header, includes it in the canonical error envelope, and attaches it to request/error logs.

### Canonical operational error

All operational failures target this response. `details` is optional and must be safe for the client.

```json
{
  "error": {
    "version": "1",
    "code": "VALIDATION_ERROR",
    "message": "Safe public message",
    "details": {},
    "statusCode": 400,
    "timestamp": "2026-08-31T00:00:00.000Z",
    "path": "/resource",
    "method": "POST",
    "requestId": "11111111-1111-4111-8111-111111111111"
  }
}
```

Stable recovery families are validation (`VALIDATION_ERROR`), session/authentication (`AUTHENTICATION_REQUIRED`), authorization (`AUTHORIZATION_DENIED`), missing resource (`NOT_FOUND`), busy/conflict (`CONFLICT`, `IMPORT_IN_PROGRESS`), reconnect (`GMAIL_RECONNECT_REQUIRED`), retryable provider validation (`GMAIL_VALIDATION_UNAVAILABLE`), export validation (`INVALID_CSV_FORMAT`, `UNKNOWN_EXPORT_PROVIDER`, `NO_VALID_EXPORT_ORDERS`), persistence (`DATABASE_ERROR`), and unexpected failure (`INTERNAL_ERROR`). Rate limiting uses `RATE_LIMIT_EXCEEDED` and may include retry metadata.

The app transport validates this complete envelope once. Malformed, legacy, or status-mismatched payloads are converted to a generic HTTP failure and their nested messages/codes are not trusted.

### Canonical success DTO families

- `AuthSession`: `{ userId, email, accessToken, refreshToken, user: { id, email, createdAt, emailVerified } }`.
- `TokenPair`: `{ accessToken, refreshToken }`.
- `OperationResult`: `{ success: true, message, ...operation-specific committed counts }`.
- `ReceiptPage`: `{ items: ReceiptDto[], pageInfo: { page, limit, total, totalPages, hasMore, nextPage } }`.
- `ImportPreferences`: the normalized monitoring, provider-export, Gmail-baseline/latest-attempt, ongoing-tracking, credential-capability, activity, and durable source-coverage projection described in `SnackTrackApp/features/import-flow/contracts.ts`.
- `ImportOperationResult`: `{ success, code?, message?, counts, totalAmount, errors }`; target failures use the error envelope rather than a nominal result DTO.
- `DashboardInsightEdition` and `UserSummary`: runtime-normalized read DTOs owned by the matching app services.

Schema names below refer to the canonical DTO families above or the app normalizer named in the success column. Unless an exception is stated, operational errors pass through the central version-1 envelope.

## Migration decisions and compatibility removal register

All changes use **additive API first, migrate the app, then remove compatibility after the supported-client gate**. Account reset/delete correctness fixes may ship atomically when retaining legacy behavior would violate the committed-operation contract.

| Resource               | Target and rollout decision                                                                                                                                                                             | Compatibility/removal task recorded 2026-08-31                                                                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Errors/session         | Central client validates envelope v1 once and exposes typed code/status/retry semantics. Public endpoint 401 stays an auth result; protected endpoint refresh exhaustion alone becomes session-expired. | Completed 2026-08-31: route failures use envelope v1 and the app no longer extracts endpoint messages.                                                                                        |
| Pagination/receipts    | Canonical `items/pageInfo` is live; token identity, parameterized query keys, and strict response/database validation are authoritative.                                                                | Completed 2026-08-31: removed snake-case/`_id` aliases, the `createdAt` fallback, temporary query `userId`, old `data/pagination`, and the dashboard compatibility barrel.                    |
| Import preferences     | Provider-specific export states, sticky Gmail baseline/latest attempt, source coverage, canonical Gmail connection health, and tracking consent/runtime remain independent axes.                        | Completed 2026-08-31: removed aggregate export fields, the legacy `gmailImport` projection, fallback synthesis, optimistic lifecycle overrides, and the separate Gmail-status frontend cache. |
| Gmail/import operation | Success uses canonical operation counts; failures use envelope v1 with stable busy/reconnect/retry codes.                                                                                               | Completed 2026-08-31: removed result-shaped failures and message matching.                                                                                                                    |
| CSV/export upload      | Rename frontend ownership to provider-export upload while retaining `/csv/import` and `csvFile` additively for released clients.                                                                        | Remove optional `success`, legacy upload response fields, `userId` multipart ownership, and historical naming after the endpoint/version rollout gate.                                        |
| Auth/session           | One validated `AuthSession`; explicit OTP outcome codes; account deletion is a committed destructive result.                                                                                            | Completed 2026-08-31: fixtures cover auth responses; deletion failure retains local credentials.                                                                                              |
| Reset/clear/delete     | Three separate operation DTOs and contracts. Reset/clear preserve session; deletion clears session only after committed success.                                                                        | Completed 2026-08-31: partial deletion sequences and stale invalidation-only behavior were removed.                                                                                           |
| Analytics/dashboard    | Runtime-validated read DTOs and OpenAPI examples share canonical fixtures.                                                                                                                              | Completed 2026-08-31: TanStack owns these resources with complete query keys.                                                                                                                 |

No compatibility item may be removed solely because the API compiles. Its app consumer, query/device-cache behavior, recovery UI, cross-stack tests, and OpenAPI entry must all be migrated first.
