## Durable projection-cache fencing checkpoint

- Migration 028 adds `users.receipt_projection_revision`, an opaque PostgreSQL transaction-ID token. Statement triggers on canonical receipt insert/update/delete/truncate change the affected account's revision in the same transaction. Profile timezone/email and import-generation changes also advance it. Multiple statements within one transaction share the token; rollback restores it. It is compared for equality, never treated as a commit-order counter. Existing receipt and source values are untouched.
- `UserRepository.findProjectionProfileById` reads the profile fields and exact revision together, separately from the public/authentication user model. Summary and Home include that revision in both cache and single-flight keys. A request after a committed import, repair, reset or deletion cannot reuse an older projection or join its calculation, even with Redis unavailable or invalidation lost. Post-commit invalidation remains cleanup; the durable revision supplies correctness.
- Uncached calculations check the profile again before publishing and skip publication when it changed or the account disappeared. If an invalidation occurs after that check but before a cache write, the late value can exist only in an obsolete namespace and is never served by a current request. Such obsolete entries retain the existing cache TTL/recovery cleanup; this is not a claim of atomic physical erasure across PostgreSQL and Redis. A request that began before a commit may finish with its internally consistent earlier snapshot.
- The account-lifecycle skill preserved the existing clear/reset/delete contracts and shared writer locks. Reset advances the revision even for an already-empty account, without deleting login identity. No mailbox credentials, receipt values or associations were changed in the local account by this checkpoint. The revision is internal, with no mobile/admin/auth DTO expansion and no new client cache or navigation owner.
- Three new isolated PostgreSQL tests verify fresh/existing migration, idempotency, affected-user scoping, zero-row mutations, multi-statement commit/rollback, real row-lock serialization, profile changes, empty reset, account cascade and truncate.
